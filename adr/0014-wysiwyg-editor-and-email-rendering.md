# ADR-0014: WYSIWYG-редактор тела письма и рендеринг email

- **Status:** accepted
- **Date:** 2026-09-25

## Context

Тело рассылки редактируется в обычном `<textarea>`, сохраняется как есть,
подстановка токенов (`Campaign::fillTokens()`) выполняется `str_replace` без
экранирования, а `MailingService::sendEmail()` собирает голый `Email` из
фрагментов — без doctype, шелла, инлайн-стилей и текстовой части. Карточка
показывает тело в `<pre>`.

Требования (change `wysiwyg-email-body`):

- визуальное редактирование HTML с сохранением разметки при переключении на
  режим исходного HTML;
- обязательная санитизация тела при сохранении: только allowlist элементов,
  атрибутов и CSS-свойств;
- один и тот же рендер письма (шелл 600px, прехедер, футер, текстовая часть)
  для реальной отправки и для всех трёх предпросмотров;
- HTML-безопасная подстановка токенов, в том числе запрет токенов в значениях
  CSS-свойств;
- standalone-разметка обоих публичных результатов отписки без интерфейса CRM.

Ограничения: продукт под proprietary-лицензией (GPL-зависимости недопустимы),
Symfony 7.4 / PHP 8.5, Webpack Encore с единственным entry, изображения
хранятся вне системы, без внешних очередей (ADR-0010).

## Decision

### 1. Редактор — TipTap 2 (MIT)

Выбран TipTap 2 (`@tiptap/*` 2.27.3, MIT): модульные расширения, полный
контроль над итоговым HTML, настраиваемая схема документа. Схема расширена
глобальным атрибутом `style` на всех разрешённых узлах и марках, поддержкой
H1–H6 (кнопки H1–H3 в тулбаре), `height`/`title` изображения, атрибутов
ссылки `href`/`target`/`rel`, стилизованного блочного `div` и email-safe
table serializer с одним каноническим `tbody`, `colspan` и `rowspan`.
Code-block отключён, служебные `colwidth` и класс ссылки в схеме не
регистрируются. `pre`/code-block, `thead`, `tfoot` и устаревшие
presentation-атрибуты таблиц не входят в общий allowlist, поэтому выполняется
инвариант **allowlist санитайзера ⊆ схема редактора** и обратное условие —
санитайзер не удаляет сериализуемые TipTap атрибуты. Режим исходного HTML не
теряет вёрстку. Контракт канонический, а не побайтовый: синонимы
`b → strong`, `i → em`, `del → s`, порядок атрибутов, CSS-значения и написание
HTML-сущностей нормализуются. Один консолидированный e2e-тест проверяет все
разрешённые элементы и атрибуты, включая `div`, изображение и таблицу, и
идемпотентность второго round-trip.

Тулбар, переключатель режима и диалог вставки изображения (URL, alt, ширина;
только `https://`) написаны вручную поверх TipTap.

**Отклонено:**

- **CKEditor 5, TinyMCE 7** — GPLv2+/коммерческие лицензии: неприемлемо для
  proprietary-продукта, dual-license дороже и юридически рискованнее MIT.
- **Quill 2** (BSD) — слабая поддержка таблиц и блочного HTML, меньше
  контроля над схемой документа.
- **Собственный contenteditable без библиотеки** — высокая стоимость
  устойчивого поведения (выделение, вставка, Undo) при нулевой выгоде.

### 2. Санитизация — symfony/html-sanitizer + свой style-санитайзер

При сохранении тело проходит `CampaignBodySanitizer`
(`html_sanitizer.sanitizer.campaign_body`, `config/packages/html_sanitizer.yaml`):
allowlist элементов и атрибутов, `allowed_media_schemes: [https]`, лимит
`max_input_length: 262 144` байта. Форма ограничивает тело 200 000 символами
до санитизации; расхождение единиц измерения для multibyte-текста не меняет
конфигурацию приложения и решается отдельным серверным изменением до
production-выкладки. CSS-свойства проверяет отдельный
`App\Html\CampaignStyleAttributeSanitizer` (`AttributeSanitizerInterface`):
allowlist свойств без `position`, `z-index`, `expression()`, `url(` и т. п.
Объявление, значение которого содержит токен `{{...}}`, отбрасывается, чтобы
подстановка токена после санитизации не могла добавить CSS-свойства; остальные
объявления того же `style` сохраняются. Пустой после санитизации результат —
ошибка валидации.

**Отклонено: HTMLPurifier (`mews/purifier`)** — готовый CSS-allowlist, но
свой конфиг-язык, обязательная writable-кеш-директория, агрессивная
нормализация разметки и менее удобный per-attribute API для интеграции с
Symfony DI.

### 3. Один `CampaignEmailRenderer` для отправки и предпросмотров

`templates/emails/campaign.html.twig` — полный email-документ (doctype,
шелл-таблица 600px, скрытый прехедер, футер с отпиской, `<style>` через
`|inline_css` из `twig/cssinliner-extra`). Рендерер возвращает
`{subject, html, text}` и принимает nullable tracking-pixel URL
(в предпросмотрах — `null`). `MailingService` собирает `Email` с `html()` и
`text()`; текстовая часть генерируется дефолтным конвертером из HTML.

Предпросмотры — три поверхности на том же рендере: страница
`GET /campaigns/{id}/preview`, модалка на карточке (sandbox-iframe на тот же
документ), живое превью в форме (`POST /campaigns/preview` — без `id`,
поскольку форма создания не имеет id; CSRF `campaign_preview`, без записи в
БД). Демо-значения токенов фиксированы в рендерере.

**Отклонено:**

- **Отдельный шаблон для предпросмотра** — предпросмотр обязан показывать
  ровно то, что уйдёт получателю, иначе он вводит в заблуждение.
- **Рендер тела как Twig-шаблона** — тело является пользовательским HTML, а
  не шаблоном; токены подставляются `CampaignTokenFiller`: тело получает
  `htmlspecialchars(ENT_QUOTES | ENT_SUBSTITUTE)`, прехедер заполняется
  plain-значениями, включая `{{unsubscribe_url}}`, и экранируется Twig ровно
  один раз.

### 4. Публичные результаты отписки — общий standalone-layout

`/unsubscribe/{trackingToken}` выбирает один из двух существующих результатов:
`confirmed` после первой успешной отписки или `already` при повторном переходе.
Оба шаблона наследуют общий `unsubscribe/layout.html.twig`, не наследуют
`base.html.twig`, используют инлайн-стили, содержат только заголовок и
поясняющий текст своего результата, не содержат навигации, внешних ассетов и
ссылок на приложение, а также помечены `noindex, nofollow`.

**Отклонено:** наследование внутреннего layout отклонено, поскольку публичный
маршрут не должен раскрывать интерфейс и маршруты CRM.

## Consequences

- Положительно: единый код рендера исключает расхождение «посмотрел —
  отправил»; предпросмотры и отправка всегда совпадают.
- Положительно: MIT/GPL-риск снят; схема редактора и allowlist санитайзера
  связаны явным email-safe контрактом и одним консолидированным round-trip-тестом.
- Положительно: оба публичных результата отписки не раскрывают интерфейс CRM,
  внешние ассеты и ссылки на приложение.
- Положительно: санитизация в одной точке (сохранение) защищает и карточку
  (`|raw`), и письма; токены в CSS отбрасываются на границе санитизации.
- Отрицательно: тулбар и диалог изображения — собственный код, который нужно
  поддерживать (покрыт e2e).
- Отрицательно: внешние изображения по https не гарантированно отображаются
  почтовыми клиентами (штатное поведение remote-картинок; CID отложен решением
  пользователя).
- Отрицательно: client-нормализация цветов при сериализации (`#eef` →
  `rgb(...)`) — безвредно, но формат значения в сохранённом HTML отличается
  от исходного.
- Follow-up: допустимый список CSS-свойств уточняется тестами без изменения
  спек; возврат к CID и markdown-конвертеру текстовой части — отложенные
  вопросы design.md; несоответствие лимита 200 000 символов и 262 144 байт
  санитайзера для multibyte-тел решается отдельным серверным изменением, без
  правки конфигурации приложения.
