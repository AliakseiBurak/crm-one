# Tasks: JSON import path with a browser-side LLM client

> Requires `add-organizations-csv-import` to be implemented first: this change
> reuses its import page, `ImportRun`, `ImportFileStorage`, the review table,
> the per-row transaction, the duplicate choice and the completion notice. It
> adds **no** migration.
>
> The parent is already in `src/`. Where a task names a parent symbol, it names
> the one that exists — `ImportProcessor::CHUNK_SIZE` is 20, the review route is
> `/{id}`, the replacement confirmation is the private
> `ImportController::finishReplacement()`, and the tabs component and
> `tabs.scss` already exist.

## 1. JSON Schema as the single source of truth

- [ ] 1.1 Write `resources/import/organization-import.schema.json`: a draft 2020-12 schema with a required `organizations` array of `minItems: 1` and the fields `name` (required, minLength 1, maxLength 255), `industry` (maxLength 255), `city` (maxLength 255), `website` (maxLength 255), `description`, `coursesAttended` (maxLength 255), `contacts[]` (`name` required + minLength 1, `position`, `phone` maxLength 32, `email`), `calls[]` (`date`, `notes`), `nextContact` (`date`, `purpose`). It SHALL contain no `unp`, no `is_main`, no `annualPlan` and no `format` keyword. Every property SHALL carry a description that names its own constraint. Verify: a test asserts the forbidden keys and the absence of `format`, and that every property has a description mentioning its maximum length or requiredness.
- [ ] 1.2 Declare a `pattern` on `calls[].date` and `nextContact.date` matching the date shapes of «Формат CSV-файла» (`D.M.YYYY`, `DD.MM.YYYY`, `DD.MM.YY`, `DD/MM/YYYY`, `DD,MM.YYYY`, optional trailing `_` or `.`), without the CSV entry parentheses. Add a test that feeds every date the schema accepts through `InteractionDateParser::parseDate()` and asserts none returns null, and that `31.08`, `09.04.202`, `09.04.20255` are rejected by the schema. Verify: both directions green.
- [ ] 1.3 Promote `justinrainbow/json-schema` from a transitive **dev-only** dependency (`packages-dev`, required by `php-cs-fixer` and `infection`) to a direct requirement in `composer.json`, and regenerate `composer.lock` so the package leaves `packages-dev`. Verify: `composer validate` passes, `composer show justinrainbow/json-schema` reports it under `require`, and `composer install --no-dev` in a scratch directory still autoloads `JsonSchema\Validator`.
- [ ] 1.4 Create `ImportJsonSchema` service: `path()`, `raw(): array`, `fieldDictionary(): array` (property name → description), `validate(array $payload): JsonValidationResult`. The result SHALL list every violation as `{organizationIndex, field, message}`. Verify: test — a payload with an empty `name` at index 4 and a 40-character `phone` at index 6 reports both with the correct indices.
- [ ] 1.5 Render the JSON tab prompt from `fieldDictionary()` so the prompt, the downloadable schema and the validator cannot drift, and so the model is told the date shapes, the maximum lengths and the required fields before it writes. Verify: a test asserts each schema property description appears in the rendered prompt.

## 2. JsonImportParser and the data path

- [ ] 2.1 Add `ImportRun::SOURCE_FORMAT_JSON = 'json'` next to the existing `SOURCE_FORMAT_CSV`. No migration.
- [ ] 2.2 Add `?string $industry` and `?string $city` to `OrganizationData` and to `ImportRow`, set them in `ImportProcessor::newOrganization()`, and cover them in `assertSavable()`. Verify: a unit test asserts `newOrganization()` writes both, and that an over-long industry raises `ImportRowStopped` like the other fields.
- [ ] 2.3 Parse the submitted payload — pasted text or uploaded file, handled identically: `json_decode`, then validate against `ImportJsonSchema`. Report every violation with the organization index and field; do not create a run. Verify: a test asserts a non-JSON payload and a schema-violating payload both fail with a report and leave no run, and that the same payload submitted as a file produces the identical report.
- [ ] 2.4 Map a valid payload to the same `OrganizationData` / `ContactData[]` / `CallData[]` DTOs the CSV path uses, with `calls[].date` passed verbatim to `InteractionDateParser::parseDate()` — no ISO coercion, and **not** `parseEntries()`: there is no note-continuation and no year inference on this path. `nextContact.date` uses the same call. `nextContact` becomes a planned `Call`. A missing or empty optional field yields null, never an empty string. `annualPlan` is not mapped. Verify: a test asserts `17/09/2025` is stored as 17.09.2025, that `21.10.25` becomes 2025, that `31.08` never reaches the parser (the schema rejects it first), and that an absent `industry` is null.
- [ ] 2.5 Dispatch by the run's `sourceFormat` in `ImportProcessor::processChunk()` and `persistRows()`, so a run created from CSV is parsed as CSV and a run created from JSON as JSON regardless of how the page was reached. Verify: a test creates a run of each kind, reopens each from the run list, and asserts each is parsed by its own parser.
- [ ] 2.6 Lift the record source, the row comparison and the name-at-resume-row out of `ImportController::replacementReport()`, which is presently hard-wired to `CsvParser::recordText()` and `CsvParser::organizationName()`, into a comparator that dispatches on `sourceFormat`. For JSON, two organizations differ when any field differs, independent of key order and payload formatting. Verify: a test asserts a reordered JSON answer reports no differing positions, and that a CSV replacement still reports textual differences.
- [ ] 2.7 Store the payload as the run's file — written to disk whether it was pasted (`ImportFileStorage::storeContents()`) or uploaded — and set `sourceFormat` = `json`, `totalRows` to the length of `organizations`, `processedRows` = 0. `filename` is the uploaded file's client name, or `ответ.json` for a paste. Verify: a test pastes 120 organizations and asserts totalRows = 120, that the stored file holds the payload verbatim, and that a paste yields `ответ.json`.

## 3. Controller + routes

- [ ] 3.1 Add three routes to the existing admin import controller: GET/POST `/admin/import/json`, GET `/admin/import/json-schema`, GET `/admin/import/llm`, all under the controller's existing `#[IsGranted('ROLE_ADMIN')]`. **The existing `#[Route('/{id}')]` for the review would otherwise swallow all three** — give each new route `requirements: ['id' => '0']`, matching the pattern the file already uses for `{id}`. There is no new conflict route and no new chunk-position parameter. Verify: `php bin/console debug:router | grep import` lists all six import routes, `/admin/import/json` resolves to the JSON action and not to a run, and a manager is refused with 403.
- [ ] 3.2 `json()`: accept the answer as pasted text or as an uploaded file and treat both identically; reject while a *different* run has `processedRows < totalRows`; otherwise validate, store, set `sourceFormat` = `json` and `totalRows` to the array length, and **return the administrator to the import list** — the run appears as a row of its own, and no review package is built. A run's own replacement is not a submission and SHALL NOT be rejected by that check. Verify: a test pastes a valid payload and asserts the run exists with processedRows = 0 and the response is the list; a test uploads the same payload as a file and asserts an identical run; a test pastes an invalid one and asserts rejection with the violation report and no run; a test presses «Импортировать» and asserts the package of 20 appears only then.
- [ ] 3.3 `jsonSchema()`: serve `resources/import/organization-import.schema.json` with `Content-Disposition: attachment`. Verify: a functional test asserts the download headers and that the body validates against the published contract.
- [ ] 3.4 Extend `replace()` and its private `finishReplacement()` for a JSON run: accept the replacement as pasted text or an uploaded file, validate it against the published schema, save the candidate, and redirect to the report addressed by URL as `app_import_replace` with `candidate=<storageKey>` — no server-side state between the two requests. Build the report (organization counts before/after, resume row, the organization at it, the positions within `1..processedRows` that differ in any field regardless of key order or payload formatting, and the shorter-file warning), render the confirmation page, and mutate the run only on confirmation: `filename` and `storageKey` replaced, **the previous file deleted**, `totalRows` set to the new count, `processedRows` kept, a candidate shorter than `processedRows` confirmed with a warning and the import treated as completed. The single-active-run check SHALL NOT reject a run's own replacement. No timestamp or recency information is reported. Verify: tests assert the run is unchanged before confirmation, that a reordered answer reports no differing positions, that confirming sets `totalRows` to the new count, keeps `processedRows` and removes the previous file, that a shorter candidate warns instead of failing, that an invalid replacement never reaches the confirmation page, and that a CSV run's replacement is unaffected.

## 5. LLM client (browser-side)

- [ ] 5.1 Implement the OpenAI-compatible browser client in `assets/js/`: `{ baseUrl, apiKey, model }`, `listModels()`, `send(messages, schema)`. Used by both providers, registered in `assets/app.js`. Verify: no request in the JS targets an application route; the only outbound calls are to the provider.
- [ ] 5.2 Provider presets: OpenRouter (`https://openrouter.ai/api/v1`, `Authorization: Bearer`, `HTTP-Referer`, `X-OpenRouter-Title`, models at `/api/v1/models`) and Ollama (`http://<host>:11434/v1`, any key, models at `/api/tags`). Verify: each preset issues the documented request shape.
- [ ] 5.3 Send with `response_format` carrying the published JSON Schema, and write a successful response into the JSON tab's paste field without submitting it. A provider that rejects `response_format` surfaces an error in the tab and leaves the import untouched. Verify: a test asserts the response lands in the field, that no import run is created, and that a rejection surfaces an error.
- [ ] 5.4 Hold the key in a JavaScript variable backed by `sessionStorage`; never use `localStorage`, never send it to the application, and provide «Забыть ключ». Verify: a test asserts the key is absent from `localStorage` and from every request to the application.
- [ ] 5.5 Document the `OLLAMA_ORIGINS` prerequisite in the deployment notes. Verify: the note exists.
