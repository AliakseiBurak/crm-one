## Context

Сущность `Call` (Doctrine ORM 3.x) уже имеет поля: `isDeal`, `isNoAnswer`, `campaignId`, `nextCallId` (self-ref), `organizationId`, `contactId`, `madeAt`, `madeBy`, `scheduledAt`, `notes`, `createdAt`. Добавляется `isRefusal` (boolean) для отметки отказа.

Сущность `Organization` расширяется полями `isActive` (boolean), `isOptedOut`, `optOutReason`, `optedOutAt`. Opt-out пара `isOptedOut`/`optOutReason` принадлежит только этому change: в `organization-fields-expansion` она исключена (развязка — вариант C), миграции не дублируются. Порядок архивации: `organization-fields-expansion` → этот change; CRUD-дельты этого change пишут итоговый union полей формы.

Эндпоинт `POST /organizations/{id}/opt-out` — новый REST-маршрут. Доступ по ролям: администратор всегда, менеджер — только если организация в области доступа.

Модель доступа (ADR-0006–0008, ADR-0011) не изменяется — все проверки через существующий механизм.

## Goals / Non-Goals

**Goals:**
- Добавить на `Call`: `isRefusal` (boolean, default false)
- Добавить на `Organization`: `isActive` (boolean, default true), `isOptedOut` (boolean, default false), `optOutReason` (text, nullable), `optedOutAt` (datetime, nullable)
- При сохранении звонка с `isRefusal = true` и `madeAt` → по чекбоксам: `isActive = false` и/или `isOptedOut = true`
- Сеттер `setIsOptedOut(false)` сбрасывает `optOutReason = null` и `optedOutAt = null` (перенесено из `organization-fields-expansion`)
- В форме организации: поле «Причина отказа» показывается только при `isOptedOut = true`; подтверждение при снятии отказа (восстановление в рассылках)
- В форме результата звонка: чекбокс «отказ» с условными чекбоксами «отметить организацию как неактивную» и «отметить отказ организации от рассылок»
- `POST /organizations/{id}/opt-out` — эндпоинт для программной отписки
- Токен `{{unsubscribe_url}}` в теле письма кампании; подсказка токенов на странице редактирования
- Исключать отписавшиеся организации из рассылок: при выборе адресатов и при отправке
- Статистика отписок на дашборде: прошлая неделя / текущий месяц / всего

**Non-Goals:**
- Изменение сущностей `Campaign`, `Contact`, `CampaignRecipient`
- Автоматическая рассылка уведомлений об отписке
- Массовая отписка через эндпоинт

## Decisions

### Decision 1: Типы новых полей на Call
- `isRefusal`: `boolean`, default false — отметка «отказ»
- `isDeal` остаётся без изменений

### Decision 2: Автоотписка при отказе — в хендлере сохранения звонка
**Решение**: В `CallController::save` (или Form handler) — после сохранения звонка, если `isRefusal === true` и `madeAt !== null`:
1. Проверить чекбокс «отметить организацию как неактивную» → `Organization.isActive = false`
2. Проверить чекбокс «отметить отказ организации от рассылок» → `Organization.isOptedOut = true`, установить `optOutReason` из поля формы (если передан); `optedOutAt` проставляется сеттером при переходе false→true
3. Сохранить организацию

**Альтернатива**: Doctrine EventSubscriber (preFlush) — отвергнуто; логика автоотписки принадлежит уровню контроллера/сервиса, т.к. зависит от бизнес-контекста формы, а не от состояния сущности.

### Decision 3: Эндпоинт opt-out
- `POST /organizations/{id}/opt-out`
- Тело: `{"reason": string|null}`
- Проверка: доступ через `OrganizationAccessVoter` (существующий)
- Установка через единый сеттер: `isOptedOut = true`, `optOutReason = reason`, `optedOutAt` — при переходе false→true
- Если `isOptedOut` уже true — возвращать успех (идемпотентность), причина обновляется
- Возврат: JSON с обновлённой организацией (200) или ошибкой (403/404)

### Decision 4: Сеттер-сброс optOutReason/optedOutAt при снятии отказа
**Решение**: В `Organization::setIsOptedOut(false)` — автоматический сброс `optOutReason = null` и `optedOutAt = null` в сеттере сущности (на уровне PHP, не через EventSubscriber). При переходе false→true сеттер проставляет `optedOutAt = now` (повторный `setIsOptedOut(true)` при уже установленном флаге дату не трогает). Это гарантирует, что причина и дата не болтаются в БД при снятом флаге, а `optedOutAt` соответствует последней отписке.

### Decision 4.1: Подтверждение при восстановлении в рассылках
**Решение**: При снятии чекбокса `isOptedOut` (переход true→false) в форме организации JavaScript показывает диалог подтверждения: «Восстановить организацию в рассылках?». При подтверждении — `isOptedOut = false`, `optOutReason = null`, `optedOutAt = null`. При отмене — чекбокс возвращается в состояние true. Это предотвращает случайное восстановление отписавшейся организации.

### Decision 5: Условное отображение optOutReason в форме организации
**Решение**: Поле `optOutReason` в форме:
1. **HTML/Twig**: рендерится всегда, но обёрнуто в контейнер с классом `js-opt-out-reason`. CSS: `.js-opt-out-reason { display: none; }`. JavaScript: при переключении чекбокса `isOptedOut` — показать/скрыть.
2. **Сервер**: если `isOptedOut = false` в submitted data, поле `optOutReason` игнорируется (сбрасывается в null при сохранении). Если `isOptedOut = true` — сохраняется как есть (nullable).

**Альтернатива A**: Symfony Form Events (PRE_SUBMIT) для динамического добавления/удаления поля — отвергнуто, т.к. сложнее поддерживать, а CSS-управление проще и надёжнее при повторной отправке с ошибками валидации.

**Альтернатива B**: Две отдельные формы (с причиной и без) — отвергнуто как дублирование.

### Decision 6: Поле isActive на Organization + отказ с неактивностью
**Решение**: 
- `Organization.isActive`: `boolean`, default true — метка активности компании
- При `isRefusal === true` в форме результата звонка появляются два независимых чекбокса:
  - «Отметить как неактивную» → `Organization.isActive = false`
  - «Отказ от рассылок» → `Organization.isOptedOut = true`
- В форме создания/редактирования организации — чекбокс «Активна» (по умолчанию true)
- Если ни один чекбокс не отмечен при отказе — только фиксация `isRefusal` на Call, без изменений Organization
- Чекбоксы независимы: можно отметить оба, только один или ни одного

**Альтернатива**: isActive = !isOptedOut (автоматическая связь) — отвергнуто; неактивность и отказ от рассылок — разные бизнес-понятия, клиент может быть активным но отказавшимся от рассылок и наоборот.

### Decision 7: Форма звонка — условные поля
**Решение**: В полной форме результата звонка чекбоксы «отметить организацию как неактивную»/«отметить отказ организации от рассылок» отображаются только при отмеченном отказе (`isRefusal`). В модальном окне быстрого редактирования на дашборде эти чекбоксы не отображаются — только чекбокс «Отказ» без подчинённых полей; отказ в модальном окне фиксирует только `isRefusal` на Call и не изменяет `Organization.isActive`/`Organization.isOptedOut`. Механика как в Decision 5: поля рендерятся всегда (на полной форме), скрываются CSS, показываются JS по чекбоксу; сервер игнорирует скрытые значения (isActive/isOptedOut без отказа).

### Decision 8: Токен `{{unsubscribe_url}}` в письме кампании

**Решение**: Новый токен `{{unsubscribe_url}}` добавляется в список известных токенов MailingService.

**Резолвинг**: При генерации письма для каждого `CampaignRecipient`:
- `{{unsubscribe_url}}` → `https://{domain}/unsubscribe/{recipient.tracking_token}`
- Используется существующее поле `CampaignRecipient.trackingToken` — уникальный токен уже есть для tracking-пикселя

**Роут отписки**: `GET /unsubscribe/{trackingToken}`
- Находит `CampaignRecipient` по токену
- Устанавливает `Organization.isOptedOut = true` (через отношение `recipient.organization`), `optedOutAt` проставляется сеттером
- Устанавливает `Organization.optOutReason = "Отписка из письма"`
- Показывает HTML-страницу «Вы отписались от рассылки»
- Открытый доступ (без аутентификации) — токен выступает аутентификацией
- Если токен не найден — 404 с сообщением «Ссылка устарела или недействительна»
- Если организация уже отписана — показать «Вы уже отписаны»

**Альтернатива**: Использовать отдельный opt-out токен на Organization — отвергнуто; tracking-токен уже уникален и привязан к получателю.

### Decision 9: Исключение отписавшихся организаций из рассылок
**Решение**: Правило применяется на двух уровнях:
1. **Выбор адресатов** (все пути создания: ручное добавление, «Выбрать все организации», добавление по группе): организация с `isOptedOut = true` не создаётся как `CampaignRecipient`. Ручное добавление — redirect back с flash «Организация отписана от рассылок»; массовое добавление — организация пропускается и учитывается в счётчике пропущенных.
2. **Отправка** (MailingService): перед обработкой получателя повторная проверка `isOptedOut` организации; если отписалась после добавления — получатель помечается `failed` с `errorMessage` «Организация отписана от рассылок», письмо не формируется, обработка остальных получателей продолжается.

**Альтернатива**: Фильтровать только на уровне MailingService — отвергнуто: отписанный адресат, висящий в `pending`, невидим для пользователя и порождает непонятные «failed» в интерфейсе; проверка на входе даёт предсказуемое поведение.

### Decision 10: Статистика отписок на дашборде
**Решение**: Новое поле `optedOutAt` (datetime, nullable) — проставляется при переходе `isOptedOut` false→true, сбрасывается при снятии (см. Decision 4). Три показателя блока «Отписки» с rolling-окнами:
- «Отписки: сегодня» — организации области доступа, у которых `optedOutAt` попадает в сегодня (с 00:00)
- «Отписки: 7 дней» — `optedOutAt` за последние 7 дней
- «Отписки: за 30 дней» — `optedOutAt` за последние 30 дней

Каждый показатель имеет подметрику «Из письма» — организации с `isOptedOut = true`, `optOutReason = "Отписка из письма"` и `optedOutAt` в пределах периода.

Область доступа — как у остальных показателей (ADR-0007/0008, ADR-0011): администратор — все организации, менеджер — своя область. Показатели вычисляются из данных и не хардкодятся.

**Альтернатива**: Считать отписки по `CampaignRecipient` — отвергнуто: отписка возможна не только из письма (звонок-отказ, эндпоинт, форма); источник истины — `Organization.optedOutAt`.

## Risks / Trade-offs

- **[Порядок архивации]** CRUD-дельты этого change перезаписывают требования `organizations/crud`, уже изменённые `organization-fields-expansion`. → **Mitigation**: фиксированный порядок архивации — сначала `organization-fields-expansion`, затем этот change; дельты написаны как итоговый union полей.
- **[Семантика отказа]** Если `is_refusal` и `is_deal` одновременно — что происходит? → **Mitigation**: Разрешены оба; сделка фиксирует интерес, отказ — отписку от рассылок, они не противоречат друг другу.
- **[Идемпотентность opt-out]** Повторный POST /organizations/{id}/opt-out обновляет причину. → **Mitigation**: Документировать как идемпотентный (PUT-семантика).
- **[optedOutAt перезаписывается]** Повторная отписка (после ресубскрайба) перезаписывает дату — статистика считает последние отписки. → **Mitigation**: Приемлемо; событие отписки = последний переход флага.
