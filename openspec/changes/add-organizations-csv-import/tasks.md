## 3. JSON Schema as the single source of truth

It SHALL contain no `unp`, no `is_main` and no `annualPlan`. Each property SHALL carry a description. Verify: a test asserts the forbidden keys are absent and every property has a description.
- [ ] 3.2 Promote `justinrainbow/json-schema` from a transitive to a direct requirement in `composer.json`. Verify: `composer validate` passes and the class autoloads.
- [ ] 3.3 Create `ImportJsonSchema` service: `path()`, `raw(): array`, `fieldDictionary(): array` (property name → description), `validate(array $payload): JsonValidationResult`. Verify: test — a payload with an empty `name` at index 4 and a 40-character `phone` at index 6 reports both with the correct indices.
- [ ] 3.4 Render the JSON tab prompt from `fieldDictionary()` so the prompt and the downloadable schema cannot drift. Verify: a test asserts each schema property description appears in the rendered prompt.

Verify: the backslash fixture of 4.3 yields exactly the expected record count with 10 fields each.
- [ ] 4.2 Structured header mismatch: when expected columns are missing or unexpected non-empty columns appear, return expected and actual headers. Verify: a CSV missing «Взаимодействия» returns the error listing the expected headers.
- [ ] 4.3 Fixtures under `tests/fixtures/import/`: a valid file; a file with a missing column; a file with the next-contact date variants and placeholders; a file with the multi-line «Взаимодействия» shapes; and **a file whose quoted cell ends in `\"` followed by further records** — the last one is required, because a hand-written fixture without a backslash parses identically with and without escape processing and would not catch the corruption. Assert an exact record count for that fixture. `База.csv` is never used by tests. Verify: tests pass and no fixture exceeds a few kilobytes.

## 5. InteractionDateParser (design D6a)

- [ ] 5.1 Create `InteractionDateParser`, applied only to the call-producing columns «Взаимодействия» and «Следующий контакт». Recognise the base shapes: `D.M.YYYY`, `DD.MM.YYYY`, `DD.MM.YY` (as `20YY`), `DD/MM/YYYY`, `DD,MM.YYYY`, plus a trailing `_` or `.` that is ignored. A group whose day, month and year are not all unambiguous is NOT a date. Verify: a test per accepted shape (`8.04.2025`, `17/09/2025`, `21.10.25`, `08,07.2025`, `05.11.2025_`).
- [ ] 5.2 Reject groups that are not dates, whether or not they look date-like: `(отдел кадров)`, `(+375171234567)`, `(приятная девушка)`, and the year-less or damaged-year forms `(09.04)`, `(09.04.202)`, `(09.04.20255)`. Each stays part of the surrounding text; the parser SHALL NOT infer, repair or truncate a year and SHALL NOT carry a year over from a preceding entry. Verify: a test per group asserting the text survives in the notes and no call is dated.
- [ ] 5.3 A group that starts with a date and continues with more text, such as `(26.09.2025-06.10.2025- 13.10.2025)`, is one entry dated with the first date, with the remaining text kept in the notes. Verify: a test asserts one dated call whose notes hold the whole original record.
- [ ] 5.4 Split the «Взаимодействия» cell into entries: text before the first token is an undated entry; each token starts an entry whose notes run to the next token. Verify: a test with `(25.08.2026) …\n(17.10.2025) …` yields two calls.

## 8. ImportProcessor (shared by both tabs)

- [ ] 8.1 `processChunk(ImportRun)`: read up to 25 organizations starting at `processedRows + 1` from the stored payload — the chunk position is derived, not passed in — choosing the parser by the run's `sourceFormat`, and return editable row DTOs. `totalRows` counts organizations. Verify: a test processes a run with `processedRows = 50` and asserts the chunk starts at row 51 and returns ≤ 25 rows.
- [ ] 8.2 `persistRows(ImportRun, rows[])`: for each row, one `wrapInTransaction` creating the `Organization` (`createdBy` = run creator, `website`/`city` when present, labelled «Актуальный курс» fragment in `description`, touched timestamps), the `Contact` entities and the `Call` entities (made calls with `madeBy` = run creator and no result flags, planned calls with `scheduledAt` and `madeAt` null). Increment `processedRows` by one per saved row; there is no second counter. A row with an empty name SHALL NOT be submitted — the review table blocks it. Verify: a test persists 2 rows and asserts created_by, is_main = false, the planned call shape and processedRows = 2.
- [ ] 8.3 Insert-time duplicate check inside `persistRows`: match `Organization.name` against the database at that moment, including rows inserted earlier in the same chunk or run. On conflict stop before the row and return it for the review form, which re-displays the package starting at that row with the values entered preserved, marks the conflict on the row and offers merge / create-new on it. The choice is submitted with the same approval form, and the remaining rows of the chunk are persisted in the same request. No separate dialog page and no separate endpoint. Verify: a test imports a name matching an existing organization and asserts the re-displayed package starts at that row with the entered values; a second test covers two rows with the same name in one file and asserts the chunk completes after the choice.
- [ ] 8.4 A row failure rolls back only that row, stops processing, and returns the error with the resume notice. The package is then re-displayed starting at the failed row, with the values the user entered for the following rows preserved. Verify: a test asserts no data for the failed row, earlier rows present, `processedRows` at the last saved row, and the re-displayed package starting at the failed row with the entered values intact.

## 9. Controller + routes

- [ ] 9.1 `ImportController` with `#[IsGranted('ROLE_ADMIN')]` at class level. - [ ] 9.2 `upload()`: reject while any run has `processedRows < totalRows`; otherwise validate headers and record count, store the file, create the run with `sourceFormat` = `csv`, `processedRows` = 0, redirect to review. Handle bad headers and an empty file. Verify: a test asserts rejection while a run is active.
- [ ] 9.3 `json()`: accept the response as pasted text or as an uploaded file and treat both identically; reject while a *different* run is active; otherwise validate the payload, store it, set `sourceFormat` = `json` and `totalRows` to the array length, redirect to review. Verify: a test pastes a valid payload and asserts the run; a test uploads the same payload as a file and asserts an identical run; a test pastes an invalid one and asserts rejection with the violation report.
- [ ] 9.4 `jsonSchema()`: serve `resources/import/organization-import.schema.json` with `Content-Disposition: attachment`. Verify: a functional test asserts the download headers and that the body validates against the published contract.
- [ ] 9.5 `list()`: order runs by `createdAt` DESC; show «Начать» when `processedRows` = 0, «Продолжить» when `0 < processedRows < totalRows`, nothing when `processedRows >= totalRows`. The table SHALL NOT have a column for the source format. Verify: a test covers all three states including `processedRows` above `totalRows`, and asserts no such column is rendered.
- [ ] 9.6 `review()`: derive the chunk from the run's own progress — rows `processedRows + 1 … min(processedRows + 25, totalRows)` — dispatching on `sourceFormat`, and take **no** chunk position from the request; a position supplied by the client SHALL NOT shift the chunk and no `from` parameter exists. Render the chunk as a table, with the notice that the approval form is submitted once. Redirect to the review page of a *different* unfinished `ImportRun` (most recently created) when one exists, and to the list with the completion notice when `processedRows >= totalRows`. Verify: a test opens the review page by address and asserts ≤ 25 rows with a progress indicator; a second request with the same address renders the same chunk; a request carrying a bogus position renders the same chunk; and a run other than the unfinished one redirects to it.
- [ ] 9.7 `approve()`: persist the submitted rows, redirect to the next chunk or the list; on a row failure flash the error and the resume notice and re-display the package from the failed row with the entered values preserved; on completion flash «Импортировано в этом прогоне: X, импортировано всего: Y». A row with an empty name SHALL block approval of that row. A duplicate name SHALL re-display the package from that row with the merge / create-new choice, and submitting the choice SHALL persist that row and the rest of the chunk. Verify: a test covers approval, a mid-chunk failure, completion, an empty name blocking only its own row, and the duplicate choice completing the chunk in one submission.
- [ ] 9.8 `replace()` and `confirmReplace()`: available on the import review page, validated against the format declared for the run's own source. Store the new file, build the report (counts before/after, resume row, the organization name at it, differing row numbers within the processed prefix, a row compared as the format defines a row), render the confirmation page, and mutate the run only on confirmation. The single-active-run check SHALL NOT reject a run's own replacement. No timestamp or recency information is reported. Verify: tests assert the run is unchanged before confirmation, that confirming sets `totalRows` to the new count and keeps `processedRows`, that a shorter file warns and completes, that an invalid replacement never reaches the confirmation page, and that a new run submission is still rejected.
