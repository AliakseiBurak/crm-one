Assert an exact record count for that fixture. `База.csv` is never used by tests. Verify: tests pass and no fixture exceeds a few kilobytes.

## 4. InteractionDateParser (design D6a)

- [ ] 4.1 Create `InteractionDateParser`, applied only to the call-producing columns «Взаимодействия» and «Следующий контакт». Recognise the base shapes: `D.M.YYYY`, `DD.MM.YYYY`, `DD.MM.YY` (as `20YY`), `DD/MM/YYYY`, `DD,MM.YYYY`, plus a trailing `_` or `.` that is ignored. A group whose day, month and year are not all unambiguous is NOT a date. Verify: a test per accepted shape (`8.04.2025`, `17/09/2025`, `21.10.25`, `08,07.2025`, `05.11.2025_`).
- [ ] 4.2 Reject groups that are not dates, whether or not they look date-like: `(отдел кадров)`, `(+375171234567)`, `(приятная девушка)`, and the year-less or damaged-year forms `(09.04)`, `(09.04.202)`, `(09.04.20255)`. Each stays part of the surrounding text; the parser SHALL NOT infer, repair or truncate a year and SHALL NOT carry a year over from a preceding entry. Verify: a test per group asserting the text survives in the notes and no call is dated.
- [ ] 4.3 A group that starts with a date and continues with more text, such as `(26.09.2025-06.10.2025- 13.10.2025)`, is one entry dated with the first date, with the remaining text kept in the notes. Verify: a test asserts one dated call whose notes hold the whole original record.
- [ ] 4.4 Split the «Взаимодействия» cell into entries: text before the first token is an undated entry; each token starts an entry whose notes run to the next token. Verify: a test with `(25.08.2026) …\n(17.10.2025) …` yields two calls.

## 6. ImportProcessor

- [ ] 6.1 `processChunk(ImportRun)`: read up to 25 organizations starting at `processedRows + 1` from the run's current payload (`storageKey`) — the chunk position is derived, not passed in — read with `CsvParser` — this change writes `sourceFormat` = `csv` only — and return editable row DTOs. `totalRows` counts organizations. `city` is not mapped: it is absent from the format and the chunk DTO carries no city. Verify: a test processes a run with `processedRows = 50` and asserts the chunk starts at row 51 and returns ≤ 25 rows.
- [ ] 6.2 `persistRows(ImportRun, rows[])`: persist starting from `processedRows + 1` and ignore any submitted row at or below it, so a re-submitted form inserts nothing twice and skips no source row. For each row, one `wrapInTransaction` creating the `Organization` (`createdBy` = run creator, `website` when present, labelled «Актуальный курс» fragment in `description`, `isActive` = true, `isOptedOut` = false, `unp`/`industry`/`city` left null, touched timestamps), the `Contact` entities and the `Call` entities (made calls with `madeBy` = run creator at 12:00 of the parsed date in the database time zone and no result flags; planned calls with `scheduledAt` set, `madeAt` null and `madeBy` null). Increment `processedRows` by one per saved row; there is no second counter. A row with an empty name stops the request: it is not saved, `processedRows` is not advanced, and the rows after it are not saved either. The duplicate check compares `Organization.name` through the database, so it follows the database's own text comparison. Verify: a test persists 2 rows and asserts created_by, is_main = false, the planned call shape (scheduledAt set, madeAt and madeBy null), the organization defaults, and processedRows = 2; a second test re-submits the same form and asserts nothing is created and no source row is skipped.
- [ ] 6.3 Insert-time duplicate check inside `persistRows`: match `Organization.name` against the database at that moment, including rows inserted earlier in the same chunk or run. On conflict stop before the row and return it for the review form, which re-displays the package starting at that row with the values entered preserved, marks the conflict on the row and offers merge / create-new on it. The choice is submitted with the same approval form, and the remaining rows of the chunk are persisted in the same request. No separate dialog page and no separate endpoint. Verify: a test imports a name matching an existing organization and asserts the re-displayed package starts at that row with the entered values; a second test covers two rows with the same name in one file and asserts the chunk completes after the choice.
- [ ] 6.4 A row failure rolls back only that row and stops processing. The error names the row number in the source file and what is wrong with it, and offers both ways out — correct the value in the table and approve again, or fix the source file at that row and upload it again as a replacement, which continues from the same row. The row comes back for correction in place with the values the user entered for the following rows preserved, and the rows after it are not saved. Verify: a test asserts no data for the failed row, earlier rows present, `processedRows` at the last saved row, the error naming the file row, and the re-displayed package starting at the failed row with the entered values intact and the failed row editable.

## 7. Controller + routes

- [ ] 7.1 `ImportController` with `#[IsGranted('ROLE_ADMIN')]` at class level. Routes: GET `/admin/import` (list + upload), POST `/admin/import/upload`, GET `/admin/import/{id}` (review), POST `/admin/import/{id}/approve`, GET|POST `/admin/import/{id}/replace` (report page and confirmation, candidate payload passed as `?candidate=<storageKey>`). There is no separate duplicate-conflict route: the choice posts to `/approve` with a resolution field. No server session is used: the run and the candidate file are addressed by URL. The `sourceFormat` column is created here so that the follow-up change `add-organizations-json-import` needs no migration. Verify: `php bin/console debug:router | grep import`.
- [ ] 7.2 `upload()`: reject while any run has `processedRows < totalRows`; otherwise validate headers and record count, store the file, create the run with `sourceFormat` = `csv`, `processedRows` = 0, redirect to review. Handle bad headers and an empty file. Verify: a test asserts rejection while a run is active.
- [ ] 7.3 `list()`: order runs by `createdAt` DESC; render the columns filename, total rows, processed rows, creation date, last processed date (empty while `processedRows` = 0) and actions; show «Начать» when `processedRows` = 0, «Продолжить» when `0 < processedRows < totalRows`, nothing when `processedRows >= totalRows`. The table SHALL NOT have a column for the source format. Verify: a test covers all three action states including `processedRows` above `totalRows`, asserts the last-processed date is shown for a run that saved rows and empty for one that did not, and asserts no source-format column is rendered.
- [ ] 7.4 `review()`: derive the chunk from the run's own progress — rows `processedRows + 1 … min(processedRows + 25, totalRows)` — and take **no** chunk position from the request; a position supplied by the client SHALL NOT shift the chunk and no `from` parameter exists. Render the chunk as a table without a city field. Redirect to the review page of a *different* unfinished `ImportRun` (most recently created) when one exists, and to the list with the completion notice when `processedRows >= totalRows`. Verify: a test opens the review page by address and asserts ≤ 25 rows with a progress indicator; a second request with the same address renders the same chunk; a request carrying a bogus position renders the same chunk; and a run other than the unfinished one redirects to it.
- [ ] 7.5 `approve()`: persist the submitted rows from `processedRows + 1`, ignoring rows at or below it, then redirect to the next chunk or the list. A row failure stops the request: flash an error naming the row number in the source file and what is wrong with it, plus the resume notice, and re-display the package from that row with the entered values preserved and the row editable in place; the rows after it are not saved. An empty name stops the package the same way. A duplicate name re-displays the package from that row with the merge / create-new choice, and submitting the choice persists that row and the rest of the chunk. On completion flash «Импортировано в этом прогоне: X, импортировано всего: Y». Verify: tests cover approval, a re-submitted form inserting nothing, a mid-chunk failure naming the file row, an empty name at row 13 stopping the package with rows 1–12 saved, completion, and the duplicate choice completing the chunk in one submission.
- [ ] 7.6 `replace()`: available on the import review page while `processedRows < totalRows`, validated against the format declared for the run's own source. Store the candidate file, build the report (counts before/after, resume row, the organization name at it, differing row numbers within the processed prefix, a row compared as the format defines a row), render the confirmation page at `/admin/import/{id}/replace?candidate=<storageKey>`, and leave the run untouched. The single-active-run check SHALL NOT reject a run's own replacement. No timestamp or recency information is reported. Verify: a test asserts the run and its current file are unchanged while the report is shown, and that the report is reproducible from its address.
- [ ] 7.7 Confirmation of a replacement: on confirm, set `filename` and `storageKey` to the candidate's, delete the file the run pointed at, set `totalRows` to the new count, keep `processedRows`, and flash the resume row and its organization. On cancel, keep everything as it was and delete the candidate file. A file shorter than `processedRows` warns and completes the run. No session is involved: the run and candidate come from the URL. Verify: tests assert the run points at the new file and the old one is gone after confirmation, that cancelling leaves the current file in place, that a shorter file warns and completes, that an invalid replacement never reaches the report, and that a new run submission is still rejected.
